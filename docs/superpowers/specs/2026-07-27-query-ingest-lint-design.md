# query · ingest · lint — 위키 운영 사이클 설계

작성일: 2026-07-27
상태: 설계 확정 대기
선행 스펙: `2026-07-27-confidence-notation-design.md` (표기법)

---

## 1. 목표

**위키를 만든 다음, 그것이 스스로 자라게 만든다.**

지금 codewiki는 위키를 *만드는* 도구다. 만든 뒤에 그것을 *쓰고 키우는* 절차가 없다.
이 스펙은 그 운영 사이클을 정의한다.

Karpathy의 LLM Wiki 패턴(Ingest/Query/Lint)을 코드베이스에 맞게 옮긴 것이다.

## 2. 구조 — 선순환 고리

```
   ┌──────────────────────────────────────┐
   │  1차 생성 — 위키 씨앗 뿌리기            │   ← 고리 밖. 한 번만
   │  (기존 prompts/1-generate.md)         │
   └──────────────────────────────────────┘
                    │
                    ▼
   ┌────────── 운영 사이클 ──────────────────┐
   │                                        │
   │   query ────▶ ingest ────▶ lint        │
   │   질문에 답     기록장을 보고   낡음·고아·  │
   │   못 답한 건    위키를 채움     빠진 문서   │
   │   기록장에      (요청 시에만)   찾아 연결   │
   │      ▲                          │       │
   │      └──────────────────────────┘       │
   │      채워진 위키가 다음 질문에 더 잘 답함   │
   └────────────────────────────────────────┘
```

**핵심은 셋이 나란히 있는 게 아니라 서로를 먹여준다는 것이다.**
query가 못 답한 것이 ingest의 입력이 되고, ingest가 쌓은 것을 lint가 잇는다.

## 3. 자동/수동 경계

| | 자동 | 이유 |
|---|---|---|
| **기록장에 적기** | ✅ 자동 | 사실 기록일 뿐. 위키를 건드리지 않으므로 위험이 없다 |
| **위키에 문서 쓰기** | ❌ 요청 시에만 | 위키는 사람 지식 층(L2)이다. 기계가 덮어쓰지 않는다 |

**자동 ingest를 하지 않는 이유:**

1. 선행 설계 §5.1에서 L2를 "재생성 불가, 기계가 덮어쓰지 않음"으로 규정했다
2. 모든 질문이 문서화 가치를 갖지 않는다. 일회성 질문이 많다
3. 검증 안 된 AI 추론이 위키에 쌓이면, 나중에 그것을 사실로 읽는 자기 오염이 생긴다(선행 설계 §7.3)

## 4. query

### 4.1 하는 일

질문에 답한다. 답하는 과정에서 **위키에 없어 코드를 열어봐야 했던 것**을 기록장에 남긴다.

### 4.2 사다리 — 싸게 시작해서 필요할 때만 비싸게

```
1단계  위키에서 관련 문장 찾기
2단계  facts.db 에서 현재 사실 확인
3단계  ── 기계가 "확인 필요" 판정 ──        ← 여기가 핵심
4단계  판정된 것만 코드를 연다
5단계  답변 조립 (표기법 스펙 준수)
```

### 4.3 "확인 필요"는 기계가 판정한다

**AI에게 "애매하면 코드 봐"라고 하지 않는다.** 약한 모델은 그 판단을 못 한다 —
아예 안 열어보거나 매번 다 열어본다. 둘 다 못 쓴다.

대신 기계가 규칙으로 판정해 목록을 준다:

| 판정 조건 | 어떻게 감지하나 | 예 |
|---|---|---|
| **동명이인** | `symbols` 조회 결과가 2개 이상 | `init`이 3곳에 정의됨 |
| **못 읽은 지점이 답에 영향** | 관련 파일에 `gaps` 있음 | "호출자 0개"인데 같은 파일에 못 읽은 매크로 3곳 |
| **위키가 추론임** | 라벨이 `🔍` | "백프레셔 목적으로 보인다 🔍" |
| **위키에 없음** | `depends` 매칭 실패 | 이 파일을 다루는 문서가 없음 |
| **앵커가 낡음** | 내용 해시 불일치 | 선행 설계 §6.4. 미구현 시 이 조건은 건너뜀 |

출력:

```
## ⚠ 코드를 직접 확인해야 할 것

1. `init` 이 3곳에 정의되어 있습니다 — 어느 것인지 코드로 확인하세요
     src/a.c:12  src/b.c:40  src/c.c:9
2. src/hal/can.c 에 못 읽은 매크로 3곳 — 호출자 목록이 불완전할 수 있습니다
3. 위키 문장 "큐는 백프레셔 목적" 은 추론입니다 — 근거가 확인 안 됨
```

스킬 지시: **"이 목록에 있는 것만 코드를 열어라. 목록에 없으면 열지 마라."**
판단이 아니라 목록 소비이므로 약한 모델도 지킬 수 있고, 비용이 예측 가능해진다.

### 4.4 답변 품질 — 사실 나열이 아니라 설명

현재 불만: *"너무 단순하게 정보에 기반해서 설명하는 느낌"*.
원인은 답변이 **사실 목록**이기 때문이다.

| | 예 |
|---|---|
| ❌ 사실 나열 | "handle_frame은 can.c:212에 정의. 호출자 3개. check_crc를 호출." |
| ✅ 설명 | "CAN 프레임 처리는 인터럽트에서 시작합니다. 하드웨어가 프레임을 받으면 handle_frame이 불리는데, 여기서 바로 처리하지 않고 큐에 넣습니다 — ISR에서 동적 할당을 할 수 없기 때문입니다." |

차이는 **인과와 순서**다. 그리고 **왜**가 있다.

**규칙:**

1. **사실을 나열하지 않는다.** 문장은 인과나 순서로 잇는다
2. **`decisions/`·`notes/`를 먼저 본다.** "왜"와 "함정"은 거기 있다. `files/` stub에는 없다
3. **서론을 쓰지 않는다.** 질문에 바로 답하고 부연한다
4. **모르는 것은 마지막에 모은다.** 문장 사이에 흩지 않는다
5. 답변 형식은 표기법 스펙 §5를 따른다

### 4.5 기록장에 남기는 것

```
2026-07-27  query  "CAN 프레임 처리 흐름"   위키없음 → 코드 3개 열람
2026-07-27  query  "handle_frame 호출자"    위키로 답함
```

**"코드를 열었다 = 위키에 없었다"**가 핵심 신호다. 이것이 ingest의 입력이 된다.

## 5. ingest

### 5.1 하는 일

기록장과 새로 알게 된 지식을 위키에 편입한다. **사용자가 요청할 때만 실행된다.**

### 5.2 동작

```
기록장을 보니 위키에 없어서 코드를 열어본 질문이 5개 있습니다.

  1. CAN 프레임 처리 흐름          (3회 질문됨)
  2. VARIANT_EU 와 KR 의 차이      (2회)
  3. handle_frame 등록 방식        (1회)

무엇을 문서로 만들까요?
```

**질문 횟수가 우선순위다.** 자주 물어본 것이 정말 필요한 문서다.
지금은 이 신호가 없어 fan-in 같은 간접 지표로 추측하고 있다.

### 5.3 흡수하는 기존 프롬프트

| 기존 | 언제 |
|---|---|
| `2-update.md` | 코드가 바뀌어 문서가 낡았을 때 |
| `4-capture.md` | "기억해둬" — 작업 중 알게 된 지식 |

`1-generate.md`(1차 생성)는 **흡수하지 않는다.** 고리 밖이다.

### 5.4 원칙

- 코드에 없는 지식은 **발명하지 말고 채굴한다** (git log·주석·사양서). 선행 설계 §11.2
- 못 찾으면 `.codewiki/questions.md`(사람 질문 큐)로 보낸다
- 모든 문장은 표기법 스펙의 배지와 근거를 단다

## 6. lint

### 6.1 하는 일

위키 건강검진 + **지식 연결**. Karpathy의 여섯 항목을 코드베이스에 맞게 옮긴다.

| Karpathy | codewiki | 누가 |
|---|---|---|
| stale claims | 앵커 해시가 깨짐 — 코드가 바뀌어 근거 무효 | 🔧 기계 † |
| orphan pages | 아무 문서도 링크하지 않는 문서 | 🔧 기계 |
| concepts lacking a page | **참조는 많은데 문서가 없는 파일** | 🔧 기계 |
| missing cross-references | 같은 심볼을 다루는 두 문서가 서로 안 이어짐 | 🔧 기계 |
| contradictions | 두 문서가 같은 것을 다르게 말함 | 🤖 AI |
| data gaps (웹 검색) | 우리는 웹 대신 **git log·주석·사양서 채굴** | 🤖 AI |

**여섯 중 넷이 기계로 처리된다.** 약한 모델 환경에서 중요한 성질이다 —
어려운 판정은 기계가 하고 AI는 좁은 일 둘만 한다.

여기에 기존 `cw lint`의 기계 검사(앵커 실존, 배지 규칙, 각주 무결성)가 더해진다.

> **†** stale claims 판정은 앵커 내용 해시(선행 설계 §6.4)에 의존한다.
> 그 기능은 아직 구현 전이다. **그때까지는 기존 `cw update`의 파일 단위 판정으로 대체한다** —
> 정밀도는 떨어지지만 동작은 한다. 해시가 들어오면 자동으로 정밀해진다.
> §4.3의 query 쪽 같은 조건도 동일하게 처리한다.

### 6.2 `cw coverage` 폐기

세 번째 항목("참조는 많은데 문서가 없는 파일")이 현재 `cw coverage`의 후반부다.
`app_c_domains.h`(528개 파일이 참조, 문서 없음)를 찾아낸 그 기능이다.

**즉 커버리지의 쓸모 있는 절반은 원래 lint에 속하는 일이었다.**

| | 처리 |
|---|---|
| 커버리지 % 숫자 | **폐기.** `depends` 글롭이 넓으면 부풀려져 의미가 없다 |
| "문서 없는 중요 파일" 목록 | **lint로 이동** |
| `cw coverage` 명령 | **삭제** |

## 7. 새 파일 둘

### 7.1 `wiki/log.md` — 기록장

append-only. ingest·query·lint를 시간순으로 기록한다.

```markdown
# 기록장 (자동 — 편집 금지)

| 날짜 | 연산 | 내용 | 결과 |
|---|---|---|---|
| 2026-07-27 | query | CAN 프레임 처리 흐름 | 위키없음 → 코드 3개 열람 |
| 2026-07-27 | query | handle_frame 호출자 | 위키로 답함 |
| 2026-07-28 | ingest | flows/can-frame.md 생성 | 위 질문에서 |
| 2026-07-28 | lint | 고아 2, 낡음 3 | 수정함 |
```

**기계 소유.** `wiki/files/`와 같은 취급 — 사람도 AI도 편집하지 않는다.

### 7.2 `wiki/index.md` — 주제 카탈로그

현재 `wiki/files/INDEX.md`는 **파일 목록**이다. 주제로 찾을 수단이 없다.
"인증은 어디를 보면 되나"에 답하는 목차가 필요하다.

`00-overview.md`와 역할이 겹칠 수 있다. **overview는 읽는 글, index는 찾는 표**로 구분한다.

## 8. 스킬 패키징

```
skill/
├── codewiki-query/SKILL.md
├── codewiki-ingest/SKILL.md
└── codewiki-lint/SKILL.md
```

**셋으로 나누는 이유:** 한 번에 쓰이는 것은 하나뿐인데, 합치면 매번 전부 로드한다.

**프롬프트 파일을 각 SKILL.md 안에 인라인한다.** 현재 구조의 문제는:

```
SKILL.md 로드 → "prompts/1-generate.md 를 읽어라" → Read 왕복 1회 → 그제서야 작업
```

이 왕복이 사용자가 느낀 지연이다. 특히 사내의 약한 모델은 도구 호출 왕복이 더 비싸다.

표기법 규칙(20줄 남짓)은 세 스킬에 **중복해서 넣는다.** 중복이 Read 왕복보다 싸다.

`prompts/` 디렉터리는 유지한다 — 채팅만 되는 AI를 쓰는 사용자를 위한 경로다(README 방법 B).
다만 스킬과 내용이 갈라지지 않도록 **스킬을 원본으로 삼고 prompts/를 생성**한다.

## 9. 구현 범위

**만들 것:**

| 대상 | 내용 |
|---|---|
| `cmd_context` 확장 | §4.3의 "확인 필요" 판정 절 추가 |
| `cw log` (신규) | 기록장 append/조회 |
| `cmd_lint` 확장 | §6.1의 기계 항목 4가지 |
| `cw coverage` | **삭제** — lint로 이동 |
| `skill/codewiki-{query,ingest,lint}/SKILL.md` | 신규 3개 |
| `skill/codewiki/SKILL.md` | 1차 생성 전용으로 축소 |
| `wiki/log.md`, `wiki/index.md` | 템플릿 추가 |
| `prompts/*.md` | **스킬에서 생성.** 손으로 두 벌 관리하면 반드시 갈라진다 |

### 9.1 단계 — 한 번에 다 만들지 않는다

이 스펙은 크다. 세 연산 + 새 파일 둘 + 스킬 셋 + 명령 개편이 들어 있다.
**독립적으로 가치가 나오는 순서로 쪼갠다.**

| 단계 | 내용 | 왜 이 순서 |
|---|---|---|
| **1** | `cmd_context` 확장(확인 필요 판정) + `codewiki-query` 스킬 + `wiki/log.md` | query가 고리의 시작점이다. 이것만 있어도 바로 쓸 수 있고, 기록장이 쌓이기 시작해야 2단계가 의미를 갖는다 |
| **2** | `codewiki-ingest` 스킬 | 1단계가 기록장을 채운 뒤라야 입력이 생긴다 |
| **3** | `cmd_lint` 확장 + `cw coverage` 삭제 + `codewiki-lint` 스킬 + `wiki/index.md` | 위키가 어느 정도 자란 뒤라야 고아·모순·빠진 링크가 나타난다 |

**1단계만 해도 독립적으로 쓸 수 있다.** 2·3단계는 위키가 자란 뒤에 필요해진다.

**하지 않을 것:**

- **자동 ingest** — §3
- **의미 검색** — 키워드·심볼명 매칭으로 충분. 벡터 검색은 "그럴듯한 것"을 반환해 이 설계의 목표와 반대다
- **답변을 슬라이드·차트로** — Karpathy 원문에는 있으나 코드베이스 질문에는 불필요

## 10. 미검증 가정

| # | 가정 | 틀리면 |
|---|---|---|
| 1 | 질문에서 심볼명을 뽑아 키워드 매칭하면 관련 위키 문장을 찾을 수 있다 | 검색이 부실해 query가 "위키에 없음"을 남발한다. 전문 검색 도입 검토 |
| 2 | 기록장의 질문 횟수가 문서화 우선순위의 좋은 신호다 | 신호가 약하면 fan-in 지표를 병용 |
| 3 | 스킬 3개로 나눠도 트리거가 서로 안 헷갈린다 | description을 더 뾰족하게 하거나 하나로 합친다 |

## 11. 한 줄 요약

> **query가 못 답한 것을 기록하고, ingest가 그것을 채우고, lint가 흩어진 것을 잇는다.**
> 어려운 판정은 기계가 하고 AI는 설명과 모순 찾기만 한다.
> 위키에 쓰는 것은 언제나 사람이 요청할 때만이다.
