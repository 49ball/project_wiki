# codewiki × codebase-memory-mcp — 환각 없는 코드 위키 설계

작성일: 2026-07-25
상태: 설계 확정 대기

---

## 1. 목표

**AI가 이 코드베이스를 읽을 때, 자신 있게 틀린 말을 하지 않게 만든다.**

이게 유일한 목표다. 데드코드 탐지, 마이그레이션, 포팅, 온보딩은 전부 이 목표가 달성되면
따라오는 부산물이지, 각각을 위해 따로 설계할 것이 아니다.

### 목표가 아닌 것

- **완벽한 정적 분석.** 대상은 빌드를 돌릴 수 없는 C/C++ 자동차 코드다.
  매크로·함수 포인터·`#ifdef`가 있는 한 어떤 도구도 완전할 수 없다.
- **위키를 사람이 쓰게 만들기.** 사람은 오직 사람만 답할 수 있는 질문에만 답한다.

### 대신 이렇게 바꾼다

> 정확해지려고 하지 말고 **정직해지게** 만든다.
> 모르는 부분에서 "모른다"고 말하는 시스템은 사람을 헷갈리게 하지 않는다.
> 그리고 정직한 시스템은 사람이 구멍을 하나씩 메울 수 있어서, 시간이 갈수록 실제로 정확해진다.

## 2. 전제 조건

| 항목 | 값 | 설계에 미치는 영향 |
|---|---|---|
| 대상 코드 | C/C++ 중심 임베디드·자동차 (IDL/Franca 혼재) | 가장 어려운 경우 |
| 빌드 | **돌릴 수 없음.** `compile_commands.json` 없음 | clangd 의미 해석 사용 불가 → CBM도 C/C++에선 tree-sitter 구문 수준 |
| 의존성 제약 | **없음. 정확도 우선** | CBM 바이너리 하드 의존 허용 |

**빌드를 못 돌린다는 사실이 이 설계의 가장 큰 제약이다.** CBM을 붙여도 C/C++
의미 해석(오버로드 해소, 매크로 전개, `#ifdef` 분기 선택)은 얻지 못한다.
따라서 "CBM을 붙이면 정확해진다"는 기대는 성립하지 않으며, 설계는
**구멍을 없애는 방향이 아니라 구멍을 보이게 만드는 방향**으로 간다.

## 3. 문제 정의 — AI가 코드베이스에서 환각하는 경로

| # | 경로 | 대책 |
|---|---|---|
| 1 | **동명이인을 자신 있게 설명** — `init()` 40개 중 엉뚱한 걸 읽음 | include 도달성 제약 (§6.2) |
| 2 | **낡은 주소를 근거로 추론** — 위키가 `can.c:212`라는데 코드가 밀림. 근거 없는 것보다 나쁘다 | 심볼 앵커 + 내용 해시 (§6.4) |
| 3 | **훈련 데이터의 일반 상식으로 빈칸 채우기** — 벤더 관용구를 표준 패턴으로 오해 | 커버리지 동봉 (§6.1) |
| 4 | **지도에 구멍이 있는 걸 모름** ← **가장 위험** | 미해석 대장 (§6.3) |
| 5 | **추론이 사실로 세탁됨** — 작년 `[inferred]`를 올해 사실로 인용 | 등급 전파 규칙 (§7.3) |
| 6 | **코드를 읽었으나 잘못 이해함** — 인용 주소는 진짜, 해석이 틀림 | 좁은 인용 + 기계 대조 + 재독 검증자 (§8) |

**4번이 핵심이다.** AI의 실패 모드는 "틀렸다"가 아니라 **"지도에 구멍이 있는 줄 몰랐다"**이다.
지금 cw.py도 CBM도 "찾은 것"만 넘기고 "못 찾은 것"은 넘기지 않는다. 그래서 AI는
구멍 뚫린 지도를 완전한 지도로 착각하고 확신을 갖고 답한다.

## 4. 핵심 원칙

1. **재생성 가능한 것과 불가능한 것을 물리적으로 분리한다.**
   기계가 만든 사실은 언제든 버리고 다시 만들 수 있어야 하고, 사람 지식은 절대 덮어쓰지 않는다.
2. **못 읽은 것은 숨기지 않고 기록해서 함께 넘긴다.**
   구멍이 많은 건 괜찮다. 안 보이는 게 문제다.
3. **기계가 할 수 있는 일에 AI를 쓰지 않는다.**
   매크로 전개는 프로그램이 AI보다 싸고 정확하다. 프로그램은 환각하지 않는다.
4. **기계가 답할 수 있는 사실을 위키 산문에 베껴 적지 않는다.**
   베낀 문장은 낡고, 낡은 걸 AI가 인용한다. 위키가 환각의 공급원이 된다.
5. **모든 문장은 출처와 등급을 달고 다니며, 등급은 홉을 건너 전파된다.**
6. **AI는 발명하지 않고 채굴한다.** 코드에 없는 것은 git log·주석·사양서에서 찾아오고,
   못 찾으면 사람 질문 큐로 보낸다.

## 5. 아키텍처

### 5.1 레이어

| 레이어 | 소유 | 내용 | 재생성 |
|---|---|---|---|
| **L0 원시 사실** | CBM | AST 정의·위치, include 그래프, 호출 지점(이름 토큰), 파일·모듈 구조 | 언제든 재생성 |
| **L1 제약·해소·구멍** | cw.py | 매크로 전개 결과, **미해석 대장**, include 도달성 필터, `#ifdef` 변형 인벤토리, IDL/Franca 경계, 등급 부여 | L0에서 파생, 재생성 |
| **L2 사람 지식** | AI가 채굴 + 사람이 보증 | `decisions/`, `notes/`, `glossary` — 코드에 없는 지식 | **재생성 불가. 기계가 덮어쓰지 않음** |
| **L3 산출물** | 질의 결과 | 위키 문서, 각종 리포트 | L0+L1+L2 조합 |

이미 cw.py는 `wiki/files/`를 "로봇 소유, 편집 금지"로 떼어놓고 있다. 그 원칙을 시스템 전체로 확장한 것.

### 5.2 AI의 접촉점은 하나다

```
          AI 에이전트
              │  (유일한 접촉점)
              ▼
      ┌───────────────────┐
      │  codewiki MCP     │
      └───────────────────┘
        │       │       │
        │       │       └─ 판단 조회 ──▶ L2  wiki/ (notes, decisions, glossary)
        │       └───────── 제약·구멍 ──▶ L1  .codewiki/facts.db
        └───────────────── 사실 질의 ──▶ L0  CBM (graph.db)

      반환: 사실 + 커버리지 + 판단  (셋이 항상 같이 나감)
```

**AI가 CBM에 직접 물어보면 안 된다.** 그러면 커버리지도 위키 지식도 안 붙는다.
codewiki가 CBM 앞에 서서, 세 레이어를 합쳐 하나의 답으로 만들어 내보낸다.

### 5.3 저장 위치

| 무엇 | 어디 | 커밋 |
|---|---|---|
| L0 CBM 그래프 | `.codebase-memory/graph.db.zst` | O (팀 공유, 재색인 생략) |
| L1 파생 사실 | `.codewiki/facts.db` (기존 위치 그대로) | X |
| L2 위키 | `wiki/` | O |
| 사람 질문 큐 | `.codewiki/questions.md` | O |

## 6. 환각 방지 장치

### 6.1 장치 ① — 모든 응답에 커버리지를 강제로 동봉

응답이 목록이면 안 된다. 반드시 "못 본 곳"이 붙는다.

**지금:**
```
handle_can_frame 호출자: 0곳
```

**바뀐 뒤:**
```
handle_can_frame 호출자: 0곳   ← 확인된 것

⚠ 이 질문과 관련해 해석하지 못한 부분:
   · can_table.c 에 펼치지 못한 매크로 CAN_REGISTER 3곳
   · dispatch.c:140 에 함수 포인터 대입
   → 이 안에서 이 함수를 부르고 있을 수 있습니다

관련 위키 기록:
   · notes/can-hal.md — "CAN 핸들러는 매크로로 테이블 등록됨" 👤사람 확인
```

**이 하나가 문제 #4를 직접 막는다.** 로봇이 더 똑똑해진 게 아니다. 못 펼쳤다는 사실을
숨기지 않을 뿐인데, AI의 답변이 "지우세요"에서 "확인해 보세요"로 바뀐다.

중요: 커버리지는 **질문과 관련된 것만** 골라서 붙인다. 전체 구멍 목록을 매번 붙이면
노이즈가 되어 무시된다. 그래서 §6.3의 대장이 심볼·파일에 연결되어 있어야 한다.

### 6.2 장치 ② — include 도달성으로 동명이인 좁히기

현재 cw.py의 호출 관계는 순수 이름 매칭이라 `init()`, `get()` 같은 흔한 이름에서 무너진다.
`resolve_include()`로 include 그래프는 **이미 만들고 있으므로**, 이를 제약으로 쓴다.

```
이름이 일치하는 호출 지점: 47곳
  ├─ 정의 파일을 전이적으로 include 하는 번역 단위 안: 12곳  → 후보
  └─ include 하지 않음:                                 35곳  → 기계적 배제
```

이름 기반 추정이 **이름 + include 도달성 제약** 추정으로 바뀐다. 빌드 없이도 100% 정적이고,
정확도가 크게 오른다.

**한계:** include 경로 해소가 불완전하면(빌드 없으니 `-I` 경로를 모른다) 도달성 판정도
불완전하다. 그래서 배제된 35곳은 **삭제하지 않고 "도달 불가로 판정됨"으로 보관**하며,
판정 근거를 함께 남긴다.

### 6.3 장치 ③ — 미해석 대장 (Unparsed Ledger)

**이 설계에서 가장 새로운 부분.** 파서가 포기한 지점을 1급 데이터로 기록한다.

새 테이블:

```sql
CREATE TABLE IF NOT EXISTS gaps(
  id INTEGER PRIMARY KEY,
  file TEXT,              -- 어느 파일
  line INTEGER,           -- 어느 줄
  kind TEXT,              -- macro_unexpanded | ifdef_branch | fnptr_assign
                          -- | token_paste | inline_asm | generated_code
  detail TEXT,            -- 매크로 이름 등
  affects_symbol TEXT,    -- 영향받는 심볼 (있으면)
  affects_file TEXT,      -- 영향받는 파일
  status TEXT,            -- open | filled_by_machine | filled_by_ai | answered_by_human
  resolution TEXT,        -- 메워졌다면 그 내용
  evidence TEXT           -- 근거 (매크로 전개 결과 등)
);
```

| 기록 대상 | 왜 위험한가 |
|---|---|
| 펼치지 못한 매크로 | 함수 정의나 호출을 통째로 숨김 |
| 선택 안 된 `#ifdef` 분기 | 다른 변형에서만 살아있는 코드 |
| 함수 포인터 대입 | 호출자 추적 불가 |
| `##` 토큰 붙이기 | 함수 **이름 자체**가 소스에 나타나지 않음 |
| 인라인 asm | 해석 불가 |
| 생성 코드 흔적 | 원본이 IDL/Franca일 수 있음 |

각 항목은 **영향받는 심볼·파일에 연결**되어야 §6.1이 관련 있는 것만 골라 붙일 수 있다.

빌드를 못 돌리니 구멍이 많이 나올 것이다. **많은 건 괜찮다. 보이면 하나씩 메울 수 있다.**

### 6.4 장치 ④ — 앵커에 내용 해시 추가

cw.py는 **이미 심볼 앵커(`파일#심볼`)를 지원한다**(`RE_ANCHOR_SYM`, `check_anchor`).
빠진 것은 내용 해시다.

```
지금:   ^[confirmed: src/hal/can.c:212]              ← 코드 밀리면 딴 데를 가리킴
지금:   ^[confirmed: src/hal/can.c#handle_can_frame]  ← 밀려도 살아있음. 내용 변화는 모름
바꿈:   ^[confirmed: src/hal/can.c#handle_can_frame@a3f2b1]
```

- 함수가 파일 안에서 이동 → **이름으로 찾으니 여전히 유효**
- 함수 **내용이 변경** → 해시 불일치 → **"이 문장의 근거가 낡음"이 자동 발생**

즉 맞으면 계속 맞고, 틀리면 틀렸다고 알려준다. 조용히 딴 코드를 가리키는 일이 사라진다.

**정책:** 라인 앵커(`파일:줄`)는 `cw lint`에서 경고로 강등한다. 새 문서는 심볼 앵커만 허용.
(라인 앵커밖에 못 쓰는 경우 — 함수 밖 전역 정의 등 — 는 예외로 남기되 경고를 띄운다.)

### 6.5 장치 ⑤ — 위키는 사실의 출처가 아니라 판단의 출처다

**기계가 답할 수 있는 사실을 위키 산문에 쓰지 않는다.**

> ❌ "`Server::start`는 `socket_init`을 호출한 뒤 `listen_loop`으로 들어간다"

이건 코드가 바뀌면 낡고, 낡은 걸 AI가 인용한다. 그리고 **애초에 위키에 있을 필요가 없다** —
로봇이 지금 이 순간의 코드를 보고 언제나 정확히 답할 수 있는 질문이다.

| 종류 | 누가 답하나 | 예시 |
|---|---|---|
| 기계가 답할 수 있는 것 | **실시간 질의** | 누가 이걸 부르나, 이 함수 어디 있나, 이 모듈은 뭘 참조하나 |
| 기계가 영원히 못 답하는 것 | **위키** | 왜 이렇게 만들었나, 겉보기와 달리 스레드 안전이 아니다, `0x1234` = 센서 수집 서비스, 하드웨어 제약 |

**부수 효과 — 이게 크다:**
지금 codewiki가 겪는 *"코드 조금 고쳤더니 문서가 우수수 낡음"* 문제의 근본 원인이 이것이다.
낡는 문장은 대부분 기계가 답할 수 있는 사실을 베껴 적어놓은 것들이다.
이 규칙을 적용하면 위키가 작아지고, 쓰기 쉬워지고, 거의 낡지 않는다.

**영향:** `templates/wiki/modules/_TEMPLATE.md`, `flows/_TEMPLATE.md`의 성격이 바뀐다.
`flows/`는 "호출 순서 나열"에서 **"이 흐름에서 주의할 점"**으로 이동한다.
순서 자체는 질의로 그려낸다.

## 7. 딱지 체계 — "누가 보증했나"

### 7.1 등급

기존 3단(`confirmed`/`inferred`/`unknown`)에 **보증 주체**를 추가한다.
사용자의 핵심 우려("AI가 착각해서 잘못 적어놓는 것")를 위키 안에서 **눈에 보이게** 만들기 위함.

등급은 **"누가 썼나"가 아니라 "누가 보증하나"**를 뜻한다. AI가 초안을 쓴 문장이라도
기계가 독립적으로 대조해 통과하면 🔧가 된다. 보증 주체가 신뢰도를 결정하기 때문이다.

| 딱지 | 뜻 | 신뢰도 |
|---|---|---|
| 🔧 `machine` | **기계가 보증.** 그래프·전개기와 대조해 통과함 (초안은 AI가 썼을 수 있음) | 가장 높음 |
| 👤 `human` | 사람이 읽고 맞다고 확인 | 가장 높음 |
| 🤖 `ai` | AI가 읽고 씀 + 다른 AI가 재확인. **기계 대조는 불가능한 주장** | **착각 가능성 남음** |
| 📄 `sourced` | 코드 밖에서 채굴 (커밋·주석·사양서). 출처 필수 | 출처만큼 |
| ❓ `inferred` | 근거 못 댐. 추측 | 참고만 |

**핵심은 🤖를 🔧나 👤인 척하지 않게 만드는 것.** 없앨 순 없지만 숨지는 않는다.

### 7.1.1 기존 3단 딱지와의 대응

기존 `confirmed` / `inferred` / `unknown`은 다음과 같이 옮긴다.

| 기존 | 새 등급 |
|---|---|
| `confirmed` | 기계 대조 가능·통과 → 🔧 / 사람 확인 → 👤 / 그 외 → 🤖 |
| `inferred` | ❓ 유지 |
| `unknown` | **유지.** 등급 체계와 별개로 "알아내지 못했음"을 나타내는 값으로 남는다 |

즉 `unknown`은 없어지지 않는다. 위 5개는 **주장이 있을 때 그 주장을 누가 보증하는가**의
축이고, `unknown`은 **주장 자체가 없음**을 뜻하므로 다른 축이다. 원리 ③("못 찾은 건
모름으로 정직하게")은 그대로 유지된다.

### 7.2 시간이 지나면 좋아진다

사람이 문서를 읽다가 틀린 걸 발견하면 고치고 👤 도장을 찍는다.
**중요한 모듈부터 🤖 → 👤로 승급**한다. 안 중요한 구석은 🤖로 남아도 된다.
위키가 자라면서 실제로 믿을 만해진다.

### 7.3 등급 전파 규칙

> **추측을 근거로 쓴 문장은 사실이 될 수 없다.**

`❓inferred`인 문장을 인용한 문장은 절대 `🔧machine`/`👤human`이 될 수 없다.
`cw lint`가 이를 강제한다. 문제 #5(자기 오염)를 막는 유일한 장치다.

자기 오염 경로:
```
1주차  AI가 추측으로 씀:  "A 거쳐 B로 간다" ❓
5주차  다른 AI가 읽음:    (등급 무시) → 사실로 인용
9주차  그 위에 또 추측:   "A→B니까 C도 이럴 것"
       → 세 홉 뒤, 아주 자신만만한 창작물
```
등급이 전파되면 아홉 주 뒤 문장에도 여전히 ❓가 붙어 있어서 사람이 헷갈리지 않는다.

## 8. 구멍을 메우는 방법

### 8.1 구멍을 두 종류로 나눈다

| | 닫힌 구멍 | 열린 구멍 |
|---|---|---|
| 정의 | **답이 소스 안에 있음** | 답이 소스 밖에 있음 |
| 예 | 매크로 전개, `##` 이름 계산, 함수 포인터 **테이블 리터럴**, `#ifdef` 변형 열거 | 런타임 함수 포인터 목적지, 실제 출하 변형, 링커 스크립트 참조, 설계 의도 |
| 누가 메우나 | **프로그램** | AI (제안자/검증자) |
| 결과 등급 | 🔧 machine | 🤖 ai 또는 ❓ inferred |

### 8.2 닫힌 구멍 — AI를 쓰지 않는다

**매크로 전개기를 파이썬으로 구현한다.** 200~300줄이면 자동차 코드의 흔한 패턴을 커버한다.

이유: **프로그램은 환각하지 않는다.** 펼치거나, "못 펼치겠음"이라고 말하거나 둘 중 하나다.
AI에게 시키면 "아마 이렇게 펼쳐질 겁니다"가 나온다. 완전히 다른 물건이다.
기계가 원리적으로 할 수 있는 일에 AI를 쓰면 비용은 더 들고 신뢰도는 더 낮아진다.

전개 실패는 실패로 대장에 남긴다. 부분 구현이어도 무방하다 —
**커버하는 만큼 구멍이 줄고, 못 하는 건 정직하게 구멍으로 남는다.**

### 8.3 열린 구멍 — 제안자/검증자, 단 질문을 바꾼다

**함정:** 두 AI는 같은 데이터로 배웠다. 같은 교과서로 공부한 두 사람은 같은 문제를 똑같이 틀린다.
제안자가 그럴듯하게 틀리면 검증자도 통과시킨다. 그러면 **틀린 답에 "검증 완료" 도장**이 찍히고,
이건 검증 안 한 것보다 위험하다. 사람이 그 도장을 믿기 때문이다.

**해결: 검증자에게 던지는 질문을 바꾼다.**

| ❌ 이렇게 물으면 안 됨 | ✅ 이렇게 물어야 함 |
|---|---|
| "이 설명이 맞는 것 같나요?" | "이 주장이 나오는 **소스 줄을 인용하세요.**" |

- 줄을 못 대면 → **기각.** 그럴듯함으로는 통과 못 한다
- 기각된 것은 버리지 않고 `❓inferred`로 남기거나 **사람 질문 큐**로 보낸다
- 검증자는 **제안자의 추론 과정을 보지 않은 새 세션**에서 돈다.
  같은 문맥을 이어받으면 제안자 논리에 물들어 검증이 형식만 남는다

**비용:** 메워진 구멍은 `gaps.resolution`에 저장된다. 매번 다시 묻지 않는다.
매크로 정의가 바뀌면 해시가 깨져 그때만 재확인한다. **비용은 일회성이다.**

### 8.4 코드 오독(문제 #6)에 대한 방어

AI가 코드를 **진짜로 읽었는데 잘못 이해한** 경우. 인용 주소는 유효하고 lint도 통과한다.

```c
if (ret = check_crc(frame)) {   // = 하나 (== 아님)
    drop_frame();
}
```
→ AI: "CRC 검사에 실패하면 프레임을 버립니다 (출처: can.c:88)" — **주소는 진짜, 뜻은 반대**

**방어 3중:**

1. **좁은 인용 강제** — "이 파일 봤음"이 아니라 "이 주장은 **이 3줄**에서 나옴".
   넓게 인용하면 오류가 숨고, 좁게 인용하면 사람이 5초면 확인한다.
2. **재독 검증자** — 검증자에게 주장 + 인용된 줄만 준다(제안자 추론 과정은 안 줌).
   *"이 3줄만 보고 이 주장이 나오나?"*
   §8.3의 "두 AI는 똑같이 틀린다"는 **상상해서 답할 때** 얘기다.
   똑같은 3줄을 다시 읽는 상황에서는 오독이 겹칠 확률이 훨씬 낮다.
   **제안자/검증자 구조는 이 문제에 가장 잘 듣는다.**
3. **기계 대조** — 구조적으로 검사 가능한 주장은 AI를 안 거치고 그래프와 대조한다.
   - "X가 Y를 호출한다" → 그래프에 해당 엣지 없으면 **에러**
   - "이 함수는 can.c에 있다" → 대조
   - "락을 잡지 않는다" → 함수 본문에 락 호출 있는지 검사

   AI가 쓴 문장을 기계가 자동 채점한다. 위키 생성 시, 코드 변경 시 계속 돈다.
   통과한 주장은 🔧 등급을 받는다(§7.1).

   **§6.5와의 관계:** §6.5는 이런 사실 주장을 위키 산문에 *쓰지 말라*고 한다.
   모순이 아니다. §6.5는 그런 문장의 **개수를 줄이는** 규칙이고, 여기 기계 대조는
   **그럼에도 남는 것**(산문상 불가피하거나 §6.5를 어긴 경우)을 잡는 그물이다.
   둘이 같이 작동한다 — 줄이고, 남은 건 채점한다.

**남는 위험:** 미묘한 오해는 남는다. 그래서 §7의 🤖 딱지가 필요하다.
없앨 수 없으므로 **보이게** 만든다.

## 9. AI가 L2(위키)를 쓰는 방법 — 발명하지 말고 채굴

### 9.1 세 갈래

| 종류 | 누가 쓰나 | 등급 |
|---|---|---|
| (a) 코드에서 도출 가능 | AI가 씀 | 🤖 (기계 대조 통과 시 🔧) |
| (b) 추론 필요, 근거는 코드에 있음 | AI가 씀 | ❓ inferred |
| (c) **코드에 정보 자체가 없음** | **AI가 쓰면 발명이다** | — |

(c)의 예: 왜 이렇게 만들었나 / `0x1234`가 무슨 서비스인가(코드엔 숫자만) /
하드웨어 제약 / 벤더 납품이라 못 고침 / 실제 출하 변형.

**이건 모델이 약해서가 아니다.** 입력에 정보가 없으면 어떤 모델도 못 만든다.
모델이 좋아져도 안 풀린다. 정보가 없는데 답을 내면 그게 정의상 환각이다.

### 9.2 (c)의 우회로 — 채굴

(c)의 정보는 "세상에 없는" 게 아니라 **"코드가 아닌 다른 곳에 있는"** 것이다.

| 어디 | 뭘 캐나 |
|---|---|
| **git 커밋 메시지 / PR 설명** | "왜 이렇게 고쳤나"가 매우 자주 있음 |
| **코드 주석** (특히 한글 주석) | 함정 지식이 묻혀 있음 |
| 이슈 트래커 | 설계 논의, 버려진 대안 |
| 사양서·설계문서 | ID 매핑, 하드웨어 제약 |
| 릴리스 노트·빌드 스크립트 | 실제 출하 변형 |

AI에게 주는 지시:
> **"지어내지 말고 찾아와라. 찾으면 출처를 달아라. 못 찾으면 쓰지 말고 질문 큐에 올려라."**

결과:
```markdown
CAN 프레임을 즉시 처리하지 않고 큐에 넣는 이유:
인터럽트 문맥에서 동적 할당을 할 수 없기 때문
^[📄sourced: 커밋 a3f21b, 2023-07-11 "fix: ISR에서 동적할당 제거"]
```
발명이 아니라 **인용**이다.

### 9.3 사람 질문 큐

못 찾은 것은 `.codewiki/questions.md`에 쌓인다.

```markdown
## 사람만 답할 수 있는 질문
- [ ] 0x1A0, 0x1A4가 각각 무슨 서비스인가? (코드엔 숫자만, git log에도 없음)
      → 관련: src/can/dispatch.c#route_frame
- [ ] VARIANT_EU와 VARIANT_KR 중 실제 출하되는 것은? 둘 다인가?
      → 관련: gaps 테이블 ifdef_branch 12건
```

**사람이 위키를 쓰는 게 아니라, AI가 다 쓰고 사람은 질문 10~20개만 답한다.**
답한 내용은 `👤human` 등급으로 위키에 들어가고, 연결된 구멍이 닫힌다.

## 10. 이미 있는 것 vs 새로 만들 것

**이 설계는 갈아엎기가 아니라 확장이다.** 현재 cw.py에 이미 있는 것:

| 이미 있음 | 위치 |
|---|---|
| 심볼 앵커 `파일#심볼` | `RE_ANCHOR_SYM`, `check_anchor()` |
| `edges` 테이블의 `confidence`, `provenance` 칼럼 | `SCHEMA` |
| include 해소 | `resolve_include()` |
| `.codewiki/facts.db` (= L1 저장소) | `db_path()`, `open_db()` |
| "미확인 ≠ 없음" 철학 | `check_anchor()`가 3단 응답 반환. 파서 주석에 명시 |
| IDL/Franca 경계 연결 | `parse_idl()`, `_link_boundaries()` |
| lint / update / coverage / context 골격 | `cmd_*()` |

**새로 만들 것:**

| 새로 | 무엇 |
|---|---|
| CBM 연동 | `parse_c_cpp()` 대체. CBM CLI 호출 → L0 수신 |
| `gaps` 테이블 + 대장 수집 | §6.3 |
| 매크로 전개기 | §8.2 |
| include 도달성 필터 | §6.2 |
| `#ifdef` 변형 인벤토리 | §6.3 |
| 앵커 내용 해시 | §6.4 |
| 등급 체계 확장 + 전파 검사 | §7 |
| 기계 대조 lint | §8.4-3 |
| codewiki MCP 서버 | §5.2 |
| 채굴 프롬프트 + 질문 큐 | §9 |

**유지할 것:** `parse_idl()`, `_link_boundaries()` — CBM에 `.fidl` tree-sitter 문법이
있을 가능성이 낮고, 빌드 없는 환경에서 IDL은 인터페이스에 대한 가장 신뢰도 높은 출처다.

## 11. 단계 계획

### Phase 0 — 측정 (선행 필수)

**지금 "정확한지 모르겠다"는 상태에서 바로 통합에 들어가면, 나중에도 나아졌는지 확인할 수 없다.**

1. **CBM 가정 실측** (아래 §12의 미검증 가정)
   - `get_graph_schema`로 C/C++ `#include`가 IMPORTS 엣지로 잡히는지
   - **해소 실패한 호출 지점을 그래프에 남기는지** ← 가장 중요.
     버린다면 §6.2가 성립하지 않아 설계 수정 필요
   - `.fidl`/`.idl` 처리 여부
2. **정답 세트 구축** — 대상 코드베이스의 모듈 하나를 손으로 검증.
   실제 호출 관계 N개, 실제 정의 위치 M개
3. **같은 자로 재기** — 현재 cw.py / CBM 단독 / 통합안. 재현율·정밀도 기록

Phase 0 없이는 이후 모든 결정이 근거를 갖지 못한다.

### Phase 1 — 정직한 기반

- `gaps` 테이블 + 대장 수집 (§6.3)
- 앵커 내용 해시 (§6.4)
- 등급 체계 확장 + 전파 검사 (§7)

**CBM 없이도 즉시 가치가 나온다.** 지금 파서로도 구멍을 기록하고 보여줄 수 있다.

### Phase 2 — 사실 기반 교체

- CBM 연동, `parse_c_cpp()` 대체
- include 도달성 필터 (§6.2)
- Phase 0의 자로 개선폭 측정

### Phase 3 — 구멍 메우기

- 매크로 전개기 (§8.2)
- `#ifdef` 변형 인벤토리

### Phase 4 — AI 통합

- codewiki MCP 서버 (§5.2) — 커버리지 동봉
- 제안자/검증자 서브에이전트 (§8.3)
- 기계 대조 lint (§8.4-3)
- 채굴 프롬프트 + 질문 큐 (§9)

### Phase 5 — 위키 재편

- 템플릿 개편 (§6.5) — `flows/`, `modules/` 성격 변경
- 기존 문서 마이그레이션

## 12. 미검증 가정 (Phase 0에서 확인)

| # | 가정 | 틀리면 |
|---|---|---|
| 1 | CBM이 C/C++ `#include`에 IMPORTS 엣지를 만든다 | §6.2를 cw.py의 기존 `resolve_include()`로 수행 |
| 2 | **CBM이 해소 실패한 호출 지점을 그래프에 남긴다** | **§6.2 성립 불가.** 설계 재검토 필요 |
| 3 | CBM에 `.fidl` 문법이 없다 | 있으면 `parse_idl()` 제거 가능 |
| 4 | CBM CLI가 스크립트에서 안정적으로 호출 가능 | MCP 클라이언트를 파이썬으로 구현해야 함 |
| 5 | 빌드 없이 CBM의 C/C++ tree-sitter 파싱이 현 정규식 파서보다 유의미하게 낫다 | Phase 2를 취소하고 Phase 1·3에 집중 |

가정 2가 가장 위험하다. **여기부터 확인해야 한다.**

## 13. 하지 않는 것 (YAGNI)

- **clangd 연동** — 빌드 DB가 없으므로 무의미
- **런타임 트레이싱 / `ingest_traces`** — 실행 불가 환경
- **데드코드·마이그레이션 전용 명령** — §6.1의 커버리지 붙은 질의를 쓰는 소비자일 뿐.
  기반이 정직해지면 자동으로 따라온다. 별도 설계하지 않는다
- **CBM의 벡터 검색(`semantic_query`)** — 의미 검색은 "그럴듯한 것"을 반환하며,
  이 설계의 목표(정직함)와 방향이 반대다. 필요해지면 나중에, 결과에 ❓ 등급을 붙여서
- **다국어 확장** — 대상은 C/C++/IDL. 158개 언어는 이 프로젝트에 무의미

## 14. 한 줄 요약

> **완벽하게 만들 수 없으니, 정직하게 만든다.**
> 기계가 할 수 있는 건 기계가 하고, 못 하는 건 못 한다고 기록하고,
> AI는 지어내지 않고 찾아오고, 모든 문장은 누가 보증했는지를 달고 다닌다.
> 그러면 AI가 착각해도 사람이 그걸 사실로 착각하지 않는다.
