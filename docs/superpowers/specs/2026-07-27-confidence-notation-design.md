# 신뢰도 표기법 설계 — 위키와 query 응답

작성일: 2026-07-27
상태: 설계 확정 대기

---

## 1. 목표

**신뢰도는 한눈에 보이고, 근거는 문장을 방해하지 않게 한다.**

이 스펙은 표기 형식만 다룬다. query 스킬 구조나 문장 자체의 품질은 별도 스펙이다(§9).

## 2. 문제

현재 표기:

```markdown
Server::start는 accept 루프를 시작한다. ^[confirmed: sym:src/net/server.cpp#Server::start]
큐 크기 제한은 백프레셔 목적으로 보인다. ^[inferred]
```

실사용에서 확인된 문제 넷:

| # | 문제 | 근거 |
|---|---|---|
| 1 | **신뢰도가 안 보인다** | `confirmed`와 `inferred`가 `^[...]` 안에 똑같이 숨어 있어, 안을 읽어야 구분된다 |
| 2 | **앵커가 문장을 밀어낸다** | `^[confirmed: sym:src/net/server.cpp#Server::start]` = 44자. 그중 실제 정보는 `Server::start` 13자뿐 |
| 3 | **query 응답이 못 읽을 물건이 된다** | query가 위키 표기를 그대로 옮겨 답해, 문장마다 44자가 끼어든다 ← **가장 아픈 지점** |
| 4 | **`^[inferred]`가 막다른 길이다** | 근거를 안 적어 나중에 아무도 검증할 수 없다 |

4번이 특히 중요하다. 지금 구조는 "틀릴 수 있음"만 말하고 **왜 그렇게 판단했는지는 버린다.**
그러면 설계 §7.2의 "시간이 지나면 🤖→👤로 승급한다"가 불가능하다 — 확인할 대상이 없기 때문이다.

## 3. 핵심 원칙

> **저장 형식과 표시 형식을 분리한다. 다만 둘을 가능한 한 닮게 만든다.**

- **위키(Obsidian)** = 저장소. 출처를 줄여 쓰지 않는다. 이 파일만 보고 검증이 되어야 한다
- **터미널(query)** = 사람이 읽는 답변. 짧게. 이모지를 쓰지 않는다
- 둘의 문장 구조를 같게 유지해, query가 번역하다 왜곡할 여지를 줄인다

## 4. 위키 표기 (Obsidian)

### 4.1 형태

```markdown
> [!info] ✅확인 12 · 🔍추론 3 · 📄출처 1 · ❓모름 2

## 책임

- ✅ CAN 프레임을 디코딩해 상위로 올린다[^handle_frame]
- ✅ 불량 CRC 프레임은 버린다[^check_crc]
- 🔍 큐를 쓰는 건 ISR에서 동적 할당을 피하려는 것[^isr_alloc]
- 📄 설계 시 동적 할당을 금지했다[^commit_a3f21b]
- ❓ 실제 출하되는 변형이 무엇인지

## 주의점

- ⚠️ 핸들러는 매크로로 테이블 등록된다 — 호출자 없음으로 보일 수 있음[^can_table]

[^handle_frame]: `src/hal/can.c#handle_frame`
[^check_crc]: `src/hal/can.c#check_crc`
[^isr_alloc]: ISR 문맥에서 호출됨 — `src/hal/can.c:88`
[^commit_a3f21b]: 커밋 a3f21b "fix: ISR에서 동적할당 제거"
[^can_table]: `src/hal/can_table.c:12`
```

### 4.2 왜 이 형태인가

**신뢰도는 본문에, 앵커는 각주로.** 이 분리가 설계의 핵심이다.

- 이모지가 불릿 왼쪽에 세로로 정렬되어 **훑으면 신뢰도가 바로 읽힌다** (문제 1 해결)
- 긴 경로는 각주 번호 하나로 접힌다 (문제 2 해결)
- 각주를 누르면 **전체 경로**가 나온다 — 저장소로서 완전성을 잃지 않는다

**각주 라벨은 번호가 아니라 이름을 쓴다.**

```markdown
[^1]              ← AI가 문장을 추가·삭제하면 번호가 어긋난다
[^handle_frame]   ← 이름이라 어긋나지 않는다
```

표준 마크다운 각주는 임의 문자열을 라벨로 받고, 렌더러가 등장 순서대로 번호를 매긴다.
따라서 **소스에는 안정적인 이름을, 화면에는 `1, 2, 3`을** 얻는다.

### 4.3 배지

| Obsidian | 터미널 | 뜻 | 각주 필수? |
|---|---|---|---|
| ✅ | `[확인]` | 코드에서 직접 확인 | **필수** — 앵커 |
| 🔍 | `[추론]` | 정황 추론 | **필수** — 추론의 근거 |
| 📄 | `[출처]` | 코드 밖에서 채굴(커밋·주석·사양서) | **필수** — 출처 |
| ❓ | `[모름]` | 확인 못 함 | 없음 |
| ⚠️ | `[주의]` | 함정·예외 | 있으면 좋음 |

`🔍`에 근거를 강제하는 것이 기존 `^[inferred]`와의 결정적 차이다(문제 4 해결).

**`⚠️`와 터미널의 "주의 블록"은 다른 것이다.** 혼동하기 쉬우므로 구분한다:

| | 무엇 | 어디서 오나 |
|---|---|---|
| **`⚠️` 배지 / `[주의]`** | 사람·AI가 쓴 **주장**이다. "이 함수는 스레드 안전이 아니다" 같은 함정 | 위키 본문 |
| **터미널 "── 주의 ──" 블록** | 기계가 붙이는 **커버리지 경고**다. "매크로 3곳을 못 읽었습니다" | `gaps` 테이블 |

전자는 다른 배지들과 같은 층위의 주장이고, 후자는 응답 전체에 붙는 메타 정보다.
후자는 위키에 저장되지 않는다 — 질의 시점의 색인 상태에서 매번 새로 계산한다.

### 4.4 앵커 문법 단순화

| 지금 | 바꿈 |
|---|---|
| `sym:src/net/server.cpp#Server::start` | `src/net/server.cpp#Server::start` |
| `src/net/server.cpp:41` | 그대로 |

`sym:` 접두어를 없앤다. `#`이 있으면 심볼 앵커, 없으면 라인 앵커로 구분이 되므로 중복이다.
`RE_ANCHOR_SYM`을 `sym:` 없이도 받도록 고치고, 기존 `sym:` 형태도 계속 받는다(관대하게).

### 4.5 문서 상단 요약 콜아웃

```markdown
> [!info] ✅확인 12 · 🔍추론 3 · 📄출처 1 · ❓모름 2
```

**`cw`가 라벨을 세어 자동 생성·갱신한다.** 사람이나 AI가 관리하지 않는다.
`wiki/files/`와 같은 "기계 소유" 영역으로 취급해 매번 덮어쓴다.

목적: 문서를 열자마자 "이 문서는 추론이 많으니 조심해서 읽어야겠다"를 알게 하는 것.
Obsidian 기본 콜아웃이라 플러그인이 필요 없다.

## 5. 터미널 표기 (query 응답)

### 5.1 형태

```
질문: CAN 프레임은 어떻게 처리되나?

[확인 1] CAN 프레임은 handle_frame이 받아 디코딩한 뒤 상위로 올립니다.
[확인 2] CRC 검사에 실패한 프레임은 버립니다.
[추론 3] 큐에 넣는 것은 ISR에서 동적 할당을 피하기 위한 것으로 보입니다.
[출처 4] 설계 시 동적 할당을 금지했습니다.
[모름  ] 실제 출하되는 변형이 무엇인지는 알 수 없습니다.

── 출처 ─────────────────────────────────────────
  1  src/hal/can.c#handle_frame
  2  src/hal/can.c#check_crc
  3  추론 ← ISR 문맥에서 호출됨 (src/hal/can.c:88)
  4  커밋 a3f21b "fix: ISR에서 동적할당 제거"

── 주의 ─────────────────────────────────────────
  이 파일에서 매크로 3곳을 읽지 못했습니다.
  위 목록이 전부가 아닐 수 있습니다.
```

### 5.2 설계 판단

**번호를 배지 안에 넣어 왼쪽 끝에 둔다.**
한글은 터미널에서 폭이 2배라, 번호를 오른쪽 정렬하면 줄바꿈이 지저분해진다.
왼쪽에 두면 배지와 번호를 한 번에 훑을 수 있고 정렬이 깨지지 않는다.

**이모지를 쓰지 않는다.** 사내 터미널·뷰어에서 깨질 수 있다. 글자 배지는 깨지지 않는다.

**`[모름]`은 번호가 없다.** 출처가 없기 때문이다. 자리는 공백으로 채워 정렬을 유지한다.

배지 폭은 **가장 큰 번호의 자릿수에 맞춘다.** 출처가 10개를 넘으면
`[확인 10]` / `[모름   ]`처럼 한 칸 넓어진다. 고정폭으로 박아두면 두 자리에서 어긋난다.

**주의 블록은 위키에 없는 정보다.** `gaps` 테이블(설계 §6.3)에서 온다.
질문과 관련된 파일의 미해석 지점만 골라 붙인다.

## 6. lint 규칙 변경

| 규칙 | 지금 | 바꿈 |
|---|---|---|
| `confirmed`에 앵커 없음 | 에러 | 유지 (`✅`) |
| **`inferred`에 근거 없음** | **허용** | **에러** |
| **한 문장에 근거 2개 이상** | 허용 | **경고** |
| 각주 라벨이 정의되지 않음 | — | **에러** (`[^x]`는 있는데 `[^x]:`가 없음) |
| 쓰이지 않는 각주 정의 | — | **경고** (고아 각주) |
| 상단 요약 콜아웃 불일치 | — | 자동 재생성 (지적하지 않음) |

"한 문장에 근거 하나"는 미관 규칙이 아니다. 근거가 셋 붙은 문장은
**어느 근거가 어느 부분을 뒷받침하는지 아무도 모른다.** 검증이 불가능해진다.
설계 §8.4-1의 "좁은 인용 강제"와 같은 원칙이다.

## 7. 구현 범위

**바꿀 것:**

| 대상 | 내용 |
|---|---|
| `RE_LABEL` | `^[confirmed:...]` → 배지 + 각주 형태 인식 |
| `RE_ANCHOR_SYM` | `sym:` 접두어를 선택적으로 |
| `cmd_lint` | §6의 규칙 반영 |
| 새 함수 | 각주 정의 파싱, 배지↔각주 연결 검증 |
| 새 함수 | 상단 요약 콜아웃 생성·갱신 |
| `templates/wiki/*` | 템플릿 5개를 새 표기로 |
| `templates/wiki/conventions.md` | 표기 규칙 전면 개정 |
| `prompts/1-generate.md`, `2-update.md`, `4-capture.md` | 새 표기로 쓰도록 지시 변경 |
| `skill/codewiki/SKILL.md` | "절대 규칙" 항목 2 갱신 |

**하지 않을 것:**

- **기존 문서 마이그레이션 도구** — 사용자가 위키를 새로 만들기로 함. 불필요
- **query 명령 구현** — 별도 스펙(§9). 이 스펙은 *출력 형식*만 정의한다
- **이모지 대체 옵션** — Obsidian은 이모지로 확정. 터미널은 애초에 글자 배지

## 8. 미검증 가정

| # | 가정 | 틀리면 |
|---|---|---|
| 1 | Obsidian이 이름표 각주(`[^handle_frame]`)를 번호로 렌더링한다 | 번호 라벨(`[^1]`)로 되돌린다. AI가 번호를 관리해야 하므로 lint가 어긋남을 잡아야 한다 |
| 2 | Obsidian 콜아웃(`> [!info]`)이 플러그인 없이 렌더링된다 | 일반 인용문(`>`)으로 낮춘다 |
| 3 | 사내 환경에서 이모지가 깨지지 않는다 (Obsidian 한정) | 위키도 글자 배지로 통일 |

가정 1이 가장 중요하다. **첫 문서를 만든 직후 Obsidian에서 눈으로 확인해야 한다.**

## 9. 이 스펙 밖의 남은 항목

사용자가 제기한 7개 중 이 스펙이 다루는 것은 4·5번과 2번의 절반이다. 나머지:

| 항목 | 내용 | 상태 |
|---|---|---|
| 1·3 | query/ingest/lint를 스킬로 재편 (Karpathy 3연산 구조) | **다음 설계 대상** |
| 2(나머지) | query 응답의 문장 품질 — "설명이 너무 단순하다" | 스킬 설계에 포함 |
| 6 | graphify 도입 여부 | **답 나옴 — 도입 안 함.** 같은 tree-sitter 엔진이라 매크로 문제를 해결하지 못한다. 필요하면 실측 비교 가능 |
| 7 | 커버리지 % 폐기 | 별도. `depends` 글롭이 넓으면 수치가 부풀려져 의미가 없다. "다음 문서화 후보" 목록만 남긴다 |

## 10. 한 줄 요약

> **신뢰도는 본문에 노출하고, 근거는 각주로 접는다.**
> 위키는 전체 경로를 잃지 않고, 터미널은 이모지 없이 같은 구조를 유지한다.
> 그리고 추론에도 근거를 강제해, 나중에 검증할 수 있게 만든다.
