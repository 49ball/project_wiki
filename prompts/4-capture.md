# [AI 지시문] 지식 캡처 — 작업에서 배운 것을 위키에 남기기

너는 방금 이 저장소에서 작업(버그 수정, 기능 추가, 조사, 사용자와의 문답)을
마쳤다. 이번 작업에서 알게 된 것 중 **코드에 적혀 있지 않은 지식**을 위키에
남겨라. 이것이 이 위키가 "코드 요약"이 아니라 "팀의 축적된 기억"이 되는 방법이다.

## 남길 가치가 있는 것 (코드에 없는 것만)

| 종류 | 어디에 |
|---|---|
| 왜 이렇게 설계됐나, 어떤 대안이 왜 기각됐나 | `decisions/` (ADR 템플릿) |
| 겉보기와 다르게 동작하는 것, 함정, 고칠 때 같이 봐야 하는 곳 | `notes/` (노트 템플릿) |
| 코드 이름과 팀 용어가 다른 것, 도메인 개념 | `glossary.md` |
| 위키를 읽다 발견한 빈 곳·틀린 곳 | 해당 문서 직접 수정 (규칙 준수) |
| 사용자가 구두로 알려준 배경 지식 | 내용에 따라 위 중 하나 |

## 남기면 안 되는 것

- 코드가 이미 말하는 것 (함수 목록, 시그니처, 호출 관계)
- 이번 세션에만 유효한 것 (작업 진행 상황, 임시 결정)
- 확인 안 된 추측을 confirmed로 포장하는 것 — 라벨 규칙은 여기서도 그대로다.
  사용자가 말해준 것은 `- 📄 문장[^src]` 로 적고
  `[^src]: 사용자 증언, YYYY-MM-DD` 를 각주로 달아라.

## 절차

1. 이번 세션을 돌아보고 위 기준으로 남길 지식을 골라라.
   **없으면 "캡처할 것 없음"이라고 보고하고 끝내라. 억지로 만들지 마라.**
2. 중복 확인: 같은 주제의 decisions/notes가 이미 있으면 새로 만들지 말고
   그 문서를 갱신하라.
3. notes는 `notes/_TEMPLATE.md`, 결정은 `decisions/_TEMPLATE.md` 형식을 따르라.
   notes에는 반드시 `depends`(관련 파일)를 적어라 — 그래야 그 코드가 바뀔 때
   "이 노트 낡았을 수 있음"을 도구가 알려준다.
4. `cw.py lint` 통과를 확인하라.
5. 사용자에게 보고하라: 무엇을 남겼고(문서 경로), 무엇을 안 남겼는지(이유).
