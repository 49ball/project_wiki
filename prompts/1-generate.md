# [AI 지시문] 위키 초기 생성

너는 이 저장소의 지식 위키를 생성하는 에이전트다. 산출물은 `wiki/` 아래의
Markdown 문서다. 시작 전에 `wiki/conventions.md`를 읽고 그 규칙을 따르라.

## 절대 규칙

1. 코드를 위키에 복사하지 마라. anchor(`경로:라인`, `sym:경로#이름`)로 참조만 하라.
2. 주장은 **불릿 + 배지**로 쓰고 근거는 **이름표 각주**로 달아라:
   `- ✅ 문장[^ref]` / `- 🔍 문장[^why]` / `- ❓ 문장`,
   문서 하단에 `[^ref]: `경로#심볼``. ✅·🔍·📄는 각주 필수,
   **🔍에는 추론의 근거를 반드시 적어라** (없으면 lint 에러).
   confirmed는 반드시 네가 실제로 열어서 확인한 위치를 anchor로 달아야 한다.
3. facts.db(stub)에 없는 관계는 "없는 것"이 아니라 "기계가 확인 못 한 것"이다.
   특히 동적 호출, 함수 포인터, DI, C 매크로, C++ 템플릿, IDL 생성 코드와의
   연결은 색인에 안 잡힌다. 네가 코드를 읽고 찾으면 inferred로 기록하라.
4. 확신이 없으면 지어내지 말고 unknown으로 남겨라. unknown이 많은 정직한
   위키가 confirmed가 많은 거짓 위키보다 훨씬 가치 있다.
5. `wiki/files/` 아래는 절대 편집하지 마라 (자동 생성 영역).

## 절차 (순서대로)

### 0단계: 준비 확인
- `python3 <툴킷경로>/cw.py index .` 와 `stubs` 가 실행되어 있는지 확인.
  안 되어 있으면 실행하라.
- `python3 <툴킷경로>/cw.py map .` 출력을 읽어라 — 디렉터리별 규모,
  fan-in 상위 파일, 엔트리포인트 후보가 나온다.

### 1단계: 모듈 경계 정하기 (문서 쓰지 말고 목록만)
- map 출력의 **`[ ]` 체크리스트가 문서화 대상 전부다.** 개수는 기계가 정했다.
  네가 "이 정도면 충분하다"고 판단해서 줄이지 마라 — `cw lint`가 에러로 잡는다.
- 여러 디렉터리를 한 모듈로 묶는 것은 허용된다(include/import 방향이 근거).
  단 **어느 항목도 빠뜨리면 안 된다.** 묶었으면 그 모듈 문서의 `depends`에
  묶인 경로를 전부 적어라. 그래야 lint가 다뤄진 것으로 인식한다.
- 디렉터리와 모듈 경계가 다르면 다르다고 기록하라.
- 각 모듈에 대해: 이름, 포함 경로(glob), 한 줄 책임 가설.
- **목록을 먼저 전부 적어라.** 하나씩 쓰다가 중간에 멈추는 것을 막기 위함이다.

### 2단계: 모듈 문서 작성 (modules/_TEMPLATE.md 복사해서)

**1단계에서 적은 목록을 전부 소비할 때까지 끝내지 마라.**
한 모듈을 마칠 때마다 남은 개수를 세어 말하라 ("3/12 완료, 9개 남음").
중간에 요약하거나 "주요 모듈은 다뤘습니다"라고 마무리하지 마라 — 실패다.

모듈마다:
- 해당 모듈의 stub들(wiki/files/...)을 먼저 읽어 심볼 목록을 파악하라.
- **파일 전체를 읽지 마라.** 먼저 시그니처/주석/독스트링 위주로 훑고,
  fan-in이 높은 파일과 공개 인터페이스 파일만 본문을 읽어라.
- 템플릿의 섹션을 채우고, frontmatter의 depends를 모듈 경로로,
  validated_at을 현재 커밋(`git rev-parse --short HEAD`)으로 설정하라.

### 3단계: 흐름 문서 작성 (flows/_TEMPLATE.md 복사해서)
- **map의 `## 엔트리포인트 후보` 전부**에 대해 흐름을 하나씩 작성하라.
  이 목록도 기계가 정한 것이다. 몇 개가 "중요한지"를 네가 고르지 마라.
- 여러 엔트리포인트가 같은 흐름으로 합쳐지면 한 문서로 묶어도 된다.
  단 그 문서에 **어느 엔트리포인트들을 다뤘는지 명시하라.**
- 엔트리포인트가 하나도 없으면(라이브러리 성격) 모듈의 공개 인터페이스에서
  시작하는 흐름을 잡아라. 그때도 모듈 목록을 기준으로 삼는다.
- 흐름을 따라가며 필요한 함수 본문만 읽어라.
- **언어 경계(C++↔Python↔IDL)를 지나는 지점은 반드시 기록하라.**
  이것이 이 위키의 최대 가치다.
- **깊이 기준(중요): 온보딩 신입이 코드를 열지 않고 이 문서만 읽고
  흐름을 따라갈 수 있어야 한다.** 각 단계마다 (1) 무슨 일이 일어나는지,
  (2) 왜 이렇게 하는지(알 수 있으면), (3) 데이터가 어떻게 바뀌는지를
  문장으로 설명하라. "간결함"은 목표가 아니다 — 낡지 않음(anchor 참조)과
  근거(라벨)가 목표다. 단계 나열만 있는 flow 문서는 실패작이다.
- 문서 맨 위에 mermaid `sequenceDiagram` 또는 `flowchart`로 흐름 요약을
  넣어라 (Obsidian이 렌더링한다). 다이어그램의 참여자는 실제 심볼 이름을 써라.

### 4단계: 개요 작성 (00-overview.md 채우기)
- 모듈/흐름 문서가 완성된 후 마지막에 작성하라 (bottom-up).

### 5단계: 검증
- `python3 <툴킷경로>/cw.py lint .` 를 실행하고 에러를 전부 고쳐라.
- **"모듈 N개 중 M개를 다루는 문서가 없습니다" 에러가 나오면 아직 안 끝난
  것이다.** 2단계로 돌아가 남은 것을 마저 써라. 이 에러를 남긴 채
  완료를 선언하지 마라.
- 에러 0이 되면: 네가 쓴 confirmed 문장 중 10개를 무작위로 골라
  anchor를 직접 다시 열어 사실인지 재확인하라. 틀리면 고치고,
  같은 유형의 오류가 다른 문서에도 있는지 점검하라.
- 마지막으로 `python3 <툴킷경로>/cw.py update --mark-done .` 을 실행하라.

## 하지 말 것

- 파일마다 설명 문서 만들기 (stub이 이미 담당한다)
- "~일 것입니다" 같은 모호한 문장 (라벨로 확신도를 표현하라)
- **목록을 임의로 줄이기** — "주요 모듈은 다뤘습니다", "핵심 흐름 위주로
  작성했습니다" 로 끝내는 것. 무엇이 충분한지는 네가 정하지 않는다.
  기계가 준 목록을 전부 소비하고 `cw lint` 에러 0 을 확인해야 끝이다
- 코드가 이미 말하는 것을 다시 말하기 (심볼 목록, 파라미터 나열 등)
  — 단, 이것은 "짧게 쓰라"는 뜻이 아니다. 금지는 중복이지 설명이 아니다.
  코드에 없는 맥락(왜, 흐름, 데이터 변화)은 충분히 길게 써라.
